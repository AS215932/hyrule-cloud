# Expiry retention (rollout pending)

`vm_expiry_retention_enabled` defaults off until provider protection and an audited restore have been verified on a disposable VM. With the flag enabled, expiry commits a whole-VM retention manifest and deletion claim before changing the provider. `vm_retention_days` records the minimum retention deadline (default 30, range 1–365); no automatic purge is implemented.

The manifest preserves source VM, disk and snapshot identities plus original automatic power-on, HA and operation-block settings. The provider stops the complete guest, disables automatic power-on/HA restart and blocks start, resume and destroy while preserving existing operator blocks. It verifies the guest is halted and protected and that all recorded disks and snapshots remain. Firmware, UEFI variables and device metadata remain with the original VM rather than being reconstructed from incomplete inventory. This is not a separate-storage backup.

The application keeps the VM suspended, its deletion claim, DNS and its prefix allocation. It does not report destruction or recycle the guest's network identity. A customer delete retry returns `retained` after verified protection. Retries honor a persisted retention manifest even if the rollout flag is off. The stored original settings are not overwritten by a retry. Unavailable or changed inventory fails closed and leaves the claim and evidence for operator reconciliation.

Local schema order is 020→021→022→023→024. The 024 downgrade refuses while active retention or historical restore records exist. Manifest version 2 describes whole-VM retention; version 1 was an unshipped disk-only prototype and is rejected rather than guessed or converted during a provider action.

The local admin endpoint `POST /v1/admin/vms/{vm_id}/actions/restore` accepts `operation_id` (caller-generated UUID), `days` (1–365) and `reason`. It requires the existing browser admin session, CSRF token and step-up authentication. Preserve the same body and operation ID when retrying a pending or ambiguous response. The request, fixed expiry and original retention evidence are committed with an audit before the provider action. A separate completion audit and expiry update commit after provider verification. An interrupted attempt remains `restoring` and blocks expiry protection; a retry resumes the recorded operation without adding more recovery days. Account-disabled guests require account enable first.

Recovery restores original restart settings and changes only retention-owned operation blocks. It leaves the guest suspended and preserves its network allocation; start is a separate explicit admin action. Successful recovery removes the active retention row while preserving its evidence in `vm_restores`, allowing later retention cycles without overwriting history. Local endpoint tests cover request/audit durability, provider failure, replay, conflicts and repeated cycles; disposable provider recovery remains unverified.

Recovery tests also cover failed request/completion audit commits and lost commit acknowledgements. PostgreSQL 16.10 verifies the migration roundtrip and downgrade refusal with only historical recovery evidence remaining. A separate PostgreSQL test observes actual lock waiters for recovery-first, protection-first and account-disable-first orderings, and verifies that stale expiry work declines after recovery clears its claim. The superseded disk-only deletion prototype has been removed.

The admin-only `GET /v1/admin/vms/{vm_id}/retention` view returns active retention deadlines, the current pending recovery request and paginated historical outcomes. Use `limit` (1–100) and the returned `next_offset` to read older history. The active recovery is returned separately even if it is outside the selected page. Its operation ID, days and reason provide the exact retry body. Provider manifests, stored SSH configuration and provider IDs are excluded. Historical outcomes remain available after the application VM row is removed.

Outstanding before rollout: pending-recovery operator workflow, status/deadline UI integration, explicit purge policy and implementation, protection monitoring, deployed-XO version checks, and disposable data/boot restoration proof. Expiration of the recorded retention deadline alone does not authorize the current code to delete anything. Production promotion remains controlled by network-operations after CI/review and coordinated API/worker quiescence.
