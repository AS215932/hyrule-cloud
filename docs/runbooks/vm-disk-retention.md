# Expiry retention (rollout pending)

`vm_expiry_retention_enabled` defaults off until provider protection and an audited restore have been verified on a disposable VM. With the flag enabled, expiry commits a whole-VM retention manifest and deletion claim before changing the provider. `vm_retention_days` records the minimum retention deadline (default 30, range 1–365); no automatic purge is implemented.

Only an initial expiry claim can create retention evidence. A previously committed deletion claim without evidence continues its original deletion, including explicit customer/admin deletions and claims made before retention was enabled. Enabling the flag does not convert those pending deletions into retention. The manifest and claim are committed atomically, so interrupted retention attempts remain distinguishable and retryable.

Automatic expiry sweeps exclude completed retention and active recovery at candidate selection and recheck the state under the lifecycle fence. Prepared retention remains retryable. Explicit internal protection reconciliation uses `destroy_vm(..., reconcile_retention=True)` without an expiry cutoff; this requires existing retention evidence and stops if recovery has already removed it. Ordinary deletion is not a substitute for reconciliation. A separate worker task periodically verifies completed retention; independent alert rules remain a rollout prerequisite.

The manifest preserves source VM, disk and snapshot identities plus original automatic power-on, HA and operation-block settings. The provider stops the complete guest, disables automatic power-on/HA restart and blocks start, resume and destroy while preserving existing operator blocks. It verifies the guest is halted and protected and that all recorded disks and snapshots remain. Firmware, UEFI variables and device metadata remain with the original VM rather than being reconstructed from incomplete inventory. This is not a separate-storage backup.

The application keeps the VM suspended, its deletion claim, DNS and its prefix allocation. It does not report destruction or recycle the guest's network identity. A customer delete retry returns `retained` after verified protection. Retries honor a persisted retention manifest even if the rollout flag is off. The stored original settings are not overwritten by a retry. Unavailable or changed inventory fails closed and leaves the claim and evidence for operator reconciliation.

Local schema order is 020→021→022→023→024→025. Migration 025 adds durable verification timestamps, a generic failure code and the next scheduled check; its downgrade removes only this telemetry. The 024 downgrade refuses while active retention or historical restore records exist. Manifest version 2 describes whole-VM retention; version 1 was an unshipped disk-only prototype and is rejected rather than guessed or converted during a provider action.

The local admin endpoint `POST /v1/admin/vms/{vm_id}/actions/restore` accepts `operation_id` (caller-generated UUID), `days` (1–365) and `reason`. It requires the existing browser admin session, CSRF token and step-up authentication. Preserve the same body and operation ID when retrying a pending or ambiguous response. The request, fixed expiry and original retention evidence first commit with a request audit. A second transaction commits the future VM expiry and an authorization audit while retaining the deletion claim and active recovery evidence. Only then can a third transaction restore provider settings, verify the guest and commit the completion audit and claim removal. An interrupted attempt remains `restoring` and blocks expiry protection; a retry resumes the recorded operation without adding more recovery days. Account-disabled guests require account enable first.

Recovery restores original restart settings and changes only retention-owned operation blocks. It leaves the guest suspended and preserves its network allocation; start is a separate explicit admin action. Successful recovery removes the active retention row while preserving its evidence in `vm_restores`, allowing later retention cycles without overwriting history. Local endpoint tests cover request/audit durability, provider failure, replay, conflicts and repeated cycles; disposable provider recovery remains unverified.

Recovery tests also cover failed request/completion audit commits and lost commit acknowledgements. PostgreSQL 16.10 verifies the migration roundtrip and downgrade refusal with only historical recovery evidence remaining. A separate PostgreSQL test observes actual lock waiters for recovery-first, protection-first and account-disable-first orderings, and verifies that stale expiry work declines after recovery clears its claim. The superseded disk-only deletion prototype has been removed.

The admin-only `GET /v1/admin/vms/{vm_id}/retention` view returns active retention deadlines, the current pending recovery request and paginated historical outcomes. Use `limit` (1–100) and the returned `next_offset` to read older history. The active recovery is returned separately even if it is outside the selected page. Its operation ID, days and reason provide the exact retry body. Provider manifests, stored SSH configuration and provider IDs are excluded. Historical outcomes remain available after the application VM row is removed.

Recovery checks the owner's current enabled state under the account/VM lifecycle lock. It need not wait for an already-queued account-enable job to clear old suspension provenance. On completion the VM remains manually suspended by the recovery operator; a delayed account-enable job cannot automatically start it. Starting the recovered VM requires a separate explicit action.

All recovery transactions also revalidate the administrator under the ordered
administrator-account fence. Revocation after request acceptance but before
provider dispatch leaves the audited operation pending and makes no provider
change. An enabled administrator can resume the recorded request. PostgreSQL
fixtures use separate administrator and owner identities to distinguish actor
revocation from owner-disable refusal.

Accounts with active retention require assisted deletion for either VM policy. Self-service deletion locks the account before its VMs and preserves the retained owner identity and sessions on refusal. Detachment, session revocation and account deletion commit together. The destroy policy releases its initial locks for identity-checked provider operations, then reacquires the account fence and rechecks retention and remaining VMs. Provider failures leave the account available for retry. PostgreSQL tests observe actual lock waiters for retention-first and account-detachment-first orderings; stale retention work refuses a changed owner.

Outstanding before rollout: pending-recovery operator workflow, status/deadline UI integration, explicit purge policy and implementation, protection monitoring, deployed-XO version checks, and disposable data/boot restoration proof. Expiration of the recorded retention deadline alone does not authorize the current code to delete anything. Production promotion remains controlled by network-operations after CI/review and coordinated API/worker quiescence.

## Periodic protection verification

The independent worker task checks up to `vm_retention_verify_batch_size` (default 10) due records per minute. Successful checks run again after `vm_retention_verify_interval_seconds` (default 21600); failed checks retry after `vm_retention_verify_retry_seconds` (default 900). Persisted schedules survive worker restarts and existing records remain checked when the rollout flag is off. Each provider check has a 30-second timeout.

Verification is read-only: it checks the original storage identities, halted state, disabled automatic power-on/HA and start/resume/destroy blocks. It holds the owner/VM lifecycle lock, rechecks state after acquiring it and skips records already recovered or restoring. It does not repair drift or start or delete guests. PostgreSQL tests cover verification holding recovery behind the lock and stale verification skipping a completed recovery.

The private retention response includes `verification.last_success_at`, `last_attempt_at`, `error` and `next_due_at`. Errors are `provider_verification_failed` or `lifecycle_state_changed`; backend details are not exposed. The authenticated metrics endpoint exports `hyrule_retention_verification_failures` and `hyrule_retention_verification_overdue`. Overdue means a retained record is more than five minutes past its scheduled check (or has no schedule and was created more than five minutes ago). Independent monitoring must cover these gauges and missing metrics/scrape failure before rollout.

Anonymous VM claims lock the destination account before the VM and revalidate that the account is enabled. Proven claims still refuse any deletion claim, destroyed VM or active retention record before changing ownership or consuming the management token. Retention's immutable owner identity therefore survives prepared, retained and restoring states.

Recovery operations distinguish `pending`, `authorized` and `completed`. `authorized` means the fixed future expiry and authorization audit are durable, while the active retention row and deletion claim still fence customer mutation and expiry work. Provider or completion-commit failure is retried using the same request body and operation ID; neither expiry nor audits accumulate on replay. Authorization-commit failure makes no provider call. A lost authorization acknowledgement can be retried from the persisted state. Before provider finalization, the current administrator/owner and future expiry are checked again. An expired or changed authorization is refused and requires operator reconciliation; it is not silently extended.
